# 1.1.5 Project Submission — CV-Aware Interview Practice Chatbot

## Project Summary

This app lets a candidate upload their CV and paste a job description, then practice for the interview with an AI-powered chatbot that knows exactly where the gaps are. The LLM pipeline extracts structured data from both documents, runs a chain-of-thought gap analysis (producing a 0–100 readiness score), and generates targeted interview questions from the identified gaps. The candidate then practices in a multi-turn chat — switching between three modes: **Practice** (AI coach with per-answer feedback), **Study** (AI demonstrates strong candidate answers), and **Interview** (formal hiring-manager simulation). At the end, an LLM-as-Judge model evaluates the session and produces an actionable improvement report.

The app stores every session to PostgreSQL (including full conversation history and cost estimates), uses pgvector for semantic deduplication of CVs and job descriptions, and supports both OpenRouter-hosted models and a local Ollama LLM as selectable providers.

## Key Features

1. **CV & JD Parsing** — Zero-shot and structured output prompts extract skills, experience, and role requirements from freeform text into validated Pydantic models
2. **Chain-of-Thought Gap Analysis** — Step-by-step reasoning across all JD requirements produces `MATCH / PARTIAL / GAP` categories and a 0–100 readiness score
3. **Few-Shot Question Generation** — Three example gap→question pairs in the prompt guide the model to produce targeted, role-specific interview questions
4. **Three Chat Modes** — Practice (coaching), Study (strong answers), Interview (formal simulation) — switchable mid-session
5. **LLM-as-Judge Evaluation** — `gpt-5` independently scores each Q&A pair and produces an overall readiness summary with improvement suggestions
6. **Security Guards** — Pattern-matching + LLM-based intent classification blocks jailbreaks, off-topic inputs, and prompt injection before they reach the main model
7. **Cost Tracking** — Per-prompt cost estimated and displayed in the UI; cumulative session cost tracked and logged
8. **Chat Persistence** — Full conversation history stored to PostgreSQL with model used and cost per message

## Implementation Highlights

### Reasoning models + streaming workaround
`gpt-5-mini` and `gpt-5-nano` are reasoning models that return empty `content` on the non-streaming path — the actual text comes back only through the streaming delta. The fix: all parse calls use a `chat_collect()` helper that opens a streaming connection and accumulates chunks into a single string. This is not documented clearly by OpenRouter, so it took significant debugging to identify.

### Matryoshka embeddings truncated to 256 dims
`nomic-embed-text-v2-moe` produces 768-dimensional vectors by default. We truncate to 256 dims (`embedding[:256]`) which matches the `vector(256)` schema column. This is the Matryoshka property: the first N dimensions form a complete, lower-resolution embedding. Result: 3× smaller storage and faster cosine similarity queries with minimal quality loss.

### Low reasoning effort for guard/parse calls
All non-chat LLM calls include `reasoning: {effort: "low"}` in the request body. This caps the internal reasoning chain to ~128 tokens, dramatically reducing latency and cost on calls that don't need deep reasoning (intent classification, JSON extraction).

### Synchronous guard in async-adjacent code
Gradio's `fn` generators run synchronously in a thread pool. The original async `classify_input()` was converted to a synchronous function that calls `chat()` directly, avoiding the need for `asyncio.run()` wrappers or thread-pool event loop conflicts.

### Think-tag suppression for Ollama/Qwen
Qwen3.5 streams its internal chain-of-thought inside `<think>...</think>` tags before the actual response. The UI suppresses display while an unclosed `<think>` tag is active, then strips all think blocks from the final response before storage and display.

## Security Guards

### Guard 1: Input Intent Classifier (LLM-based)
Every user message is classified by `gpt-5-nano` before reaching the main model. Categories: `LEGITIMATE`, `JAILBREAK`, `OFF_TOPIC`, `MALICIOUS`. Non-legitimate inputs are rejected immediately. The guard **fails open** (allows through) on API errors to avoid blocking legitimate users when the guard itself is unavailable.

### Guard 2: CV/JD Content Validation (pattern-based)
- Maximum input length enforced: 10,000 chars (CV), 5,000 chars (JD)
- Regex-based prompt injection detection in uploaded text
- Length and format checks before any LLM call

### Guard 3: Pydantic Output Validation
All structured LLM outputs are validated against Pydantic v2 schemas. If JSON parsing fails, `_parse_llm_json()` retries with a stripped response and logs a warning; downstream code receives a `None` result rather than a crash.

## Database Schema

PostgreSQL with `pgvector` extension. All tables use UUIDs.

```sql
sessions         — UUID, created_at
cv_profiles      — session_id, raw_text, parsed_data JSONB, embedding vector(256), created_at
job_descriptions — session_id, raw_text, parsed_data JSONB, embedding vector(256), created_at
gap_analyses     — session_id, cv_id, jd_id, analysis JSONB, readiness_score INT, created_at
chat_messages    — session_id, role, content, model_used, cost_usd, created_at
evaluations      — session_id, evaluation JSONB, overall_score INT, created_at
```

IVFFlat cosine similarity indexes on `cv_profiles.embedding` and `job_descriptions.embedding` enable fast nearest-neighbour queries.

## Deployment

Single Docker container. PostgreSQL and Ollama run on the host machine.

```bash
docker compose up --build
# App available at http://localhost:7860
```

**Required env vars** (`.env` file):
```
OPENROUTER_API_KEY=sk-or-...
DATABASE_URL=postgresql://user:password@host.docker.internal:5432/interview_app
OLLAMA_BASE_URL=http://host.docker.internal:11434
```

**Required Ollama models:**
```bash
ollama pull qwen3.5:9b
ollama pull nomic-embed-text-v2-moe
```

## Future Improvements

1. **Real-time OpenRouter pricing** — The `/api/v1/models` endpoint returns live pricing; cost estimates currently use hardcoded values
2. **Persistent user sessions** — Currently single-session; multi-user support would need authentication
3. **CV deduplication in UI** — `find_similar_cv()` / `find_similar_jd()` functions exist but dedup is not yet surfaced to the user
4. **Fine-tuned domain prompts** — Current prompts are general-purpose; domain-specific few-shot examples (engineering, finance, HR) would improve question quality
5. **Deployment to cloud** — Docker Compose is dev-only; a production deployment would use managed PostgreSQL and a container registry
